# 設計書：編集画面の送信先セレクタ（React化）

- 作成日：2026-10-23
- 関連：Issue #（作成後に記入）／前提 PR #709（React・TypeScriptのビルド環境）

## 1. 目的

1. **切り替えのラグをなくす**：編集画面で「自分／全体」を押すたびに、サーバーで画面を作り直している（本番の中央値 約450ms）。切り替えをブラウザ内（React）で完結させ、通信を0回にする。
2. **送信先を柔軟に変えられるようにする**：今は編集で「選択（ユーザー指定）」に変えられない・選んだユーザーを変更できない。誤送信や誤って全体公開したときに直せるよう、次をできるようにする。
   - 自分のみ／選択／全体 の相互の切り替え
   - 選択したユーザーの追加・削除

## 2. 範囲

| 対象 | 今回 | 理由 |
|---|---|---|
| 編集画面（`/waves/:id/edit`） | 対象 | ラグを計測した画面。機能追加の本体 |
| 編集モーダル（`edit_modal`） | 対象外 | 返信一覧から開く画面で、返信は送信先を変えられないため。後で同じ部品を使い回す |
| 新規投稿画面 | 対象外 | 同じラグがあるが、まず編集で部品を完成させてから置き換える |
| 返信（`reply?`）の投稿 | 変更不可のまま | 返信先の変更は仕様外 |
| 保存後のラグ（コールドスタート） | 対象外 | インフラ要因。別Issueで扱う |

## 3. 現状の仕組みと問題点

- 送信先ボタンはリンク（`edit_post_path(post, privacy: ...)`）で、押すたびに Turbo Frame `sending_privacy` 経由で**編集画面全体をサーバーで再描画**し、その一部だけを差し替えている。
- 公開範囲は hidden の `post[privacy]` で送信。`selected_users` の投稿は「変更できません」と表示している。
- `PostsController#update` は `recipient_ids` を受け取っても捨てている（`except(:recipient_ids, ...)`）。
- **見落としやすい点**：`Post#visible_to?` は、公開範囲が何であっても `post_users` に承認済みの行があれば閲覧を許可する。
  → 「選択」から「自分のみ」に変えるときは、`post_users` の行を削除しないと、外したはずの人が見え続ける。

## 4. 設計方針

### 4.1 全体の流れ

```
[編集画面 (Rails)]
  form_with（今のフォームのまま、通常の送信）
    └ <react-component name="RecipientSelector" props="{...}">
         ├ 自分／選択／全体 の切り替え（ブラウザ内で完結）
         ├ ユーザーのチェックリスト（選択のときだけ表示）
         └ hidden input: post[privacy], post[recipient_ids][]
  保存 → PATCH /waves/:id → PostsController#update
         └ 投稿の更新 ＋ 送信先の差分反映（1つのトランザクション）
```

- **保存はRailsのフォーム送信のまま**にする。APIを新しく作らないことで、既存の処理（カテゴリー・本文・音声の更新、エラー表示、リダイレクト）と競合しない。
- Reactは「フォームの一部の入力欄」として動くだけ。カスタム要素はフォームの中に描画されるので、Reactが出す hidden input はそのまま送信される。

### 4.2 Reactコンポーネント `RecipientSelector`

**props（Railsから渡す初期値）**

```ts
type Recipient = { id: number; displayName: string; usernameSlug: string; following: boolean };

type Props = {
  initialPrivacy: 'only_me' | 'selected_users' | 'open';
  initialRecipientIds: number[];
  candidates: Recipient[]; // フォロー中のユーザー ＋ 今の送信先（フォロー解除済みも含む）
};
```

**画面の状態（state）**

| state | 内容 |
|---|---|
| `privacy` | 今選んでいる公開範囲 |
| `selectedIds` | チェックしているユーザーのID |

**動き**

- ボタンを押すと `privacy` だけを変える（通信なし）。
- 「選択」→ 別のボタン → 「選択」と戻ったとき、**チェックした内容は残す**（誤操作で選び直しにならないように）。送信時は `privacy` が `selected_users` のときだけ `recipient_ids` を出す。
- フォロー解除済みの今の送信先は、「（フォロー解除済み）」と表示して残す。黙って外れないようにするため。
- 「選択」で0人のときは、注意文を出す（最終的な判定はサーバーで行う）。
- 送信先が減る・全体公開になるなど影響が大きい変更は、変更内容を画面に表示する（例：「2人を送信先から外します」）。確認ダイアログは今回は出さない。

### 4.3 サーバー側（Rails）

**更新の処理**（`PostsController#update`）

1. 投稿の内容を更新する（今の処理のまま）。
2. 公開範囲（`post[privacy]`）が送られてきたときだけ、送信先の差分を反映する（新しく作る `Post#update_direct_recipients!(recipient_ids)`。公開範囲は更新後の `privacy` をモデル内で参照する）。
   - `selected_users` のとき：新しいIDの行を追加、外したIDの行を削除。
   - `only_me` / `open` のとき：`direct_recipient` の行をすべて削除。
3. 1と2を**1つのトランザクション**にする。途中で失敗したら全部元に戻す。
4. **新しく追加された人にだけ**通知を送る（今の `create_notification_post` は全員に送るので、対象を指定できるようにする）。外された人には通知しない。

**入力チェック（バリデーション）**

| チェック | 失敗したとき |
|---|---|
| `selected_users` で送信先が0人 | エラー「送信先を1人以上選んでください」（422で編集画面に戻す） |
| 送信先のIDが「フォロー中のユーザー ＋ 今の送信先」に含まれない | エラー（他人を勝手に送信先にできないようにする） |
| 自分自身のID | 無視する |
| 返信の投稿で送信先・公開範囲を変えようとした | 変更しない（今の仕様のまま） |
| 投稿者本人（または管理者）以外 | 今の `set_current_user_post` で拒否済み |

## 5. 既存の処理への影響

| 既存の処理 | 影響 | 対応 |
|---|---|---|
| 新規投稿の作成（`PostCreationJob`） | なし | 触らない |
| 編集モーダル（`update_modal`） | なし | 触らない。`recipient_ids` は今まで通り無視 |
| Turbo Frame `sending_privacy` のリンク（`edit_post_path(privacy:)`） | 編集画面では使わなくなる | `edit` アクションの `params[:privacy]` の扱いは残す（モーダルが使うため） |
| 通知（`NotificationJob 'direct'`） | 新規投稿は今まで通り全員へ | 編集用に「対象を指定する」引数を追加。既存の呼び出しは変えない |
| `visible_to?` | なし | 送信先の行を正しく削除することで正しく動く |

## 6. テスト計画

**リクエストスペック（`spec/requests/posts_update_recipients_spec.rb`）**

| # | 操作 | 期待する結果 |
|---|---|---|
| 1 | 全体 → 選択（A, B） | 行が2件でき、A・Bが閲覧可能、A・Bに通知 |
| 2 | 選択（A, B）→ 選択（B, C） | Aの行が消えて見られない、Cが追加され、Cにだけ通知 |
| 3 | 選択（A）→ 自分のみ | 行が0件、Aは閲覧不可 |
| 4 | 選択（A）→ 全体 | 行が0件、誰でも閲覧可能 |
| 5 | 選択で0人 | 422、投稿は変わらない |
| 6 | フォローしていない人のIDを送る | エラー、行は増えない |
| 7 | 他人の投稿を更新 | 拒否される（既存の確認） |
| 8 | 返信の投稿で公開範囲を送る | 変わらない |
| 9 | 公開範囲を送らずに本文だけ更新（今の編集画面の「選択」の投稿） | 保存でき、送信先はそのまま、通知なし |

**フロントエンド**

- `yarn typecheck`（型チェック）と `yarn build:react` が通ること。
- 手動確認：切り替え時に通信が発生しないこと（DevToolsのNetworkで0件）、ブラウザの戻る、Turbo Frameでの移動後も表示されること。

**完了の条件**：`rubocop` と `rspec`（`compose.test.yml` で実行）がすべて通ること。

## 7. 計測（改善前後の比較）

| 項目 | 改善前 | 改善後の目標 |
|---|---|---|
| 送信先ボタンを押したときの通信 | 1回（中央値 約450ms） | 0回 |
| 押してから表示が変わるまで | 約450ms | 体感で即時（50ms未満） |

- 計測は本番環境、ログインした状態で、初回（コールドスタート）を除いて5回ずつ。

## 8. 進め方（ブランチとPRの分け方）

1. **PR① サーバー側**：`update_direct_recipients!`、バリデーション、通知の対象指定、リクエストスペック。画面は今のまま（この時点では送信先の変更はまだできない）。
2. **PR② 画面側**：`RecipientSelector` を作り、編集画面に組み込む。手動確認と計測。

サーバー側を先にする理由：外部から直接リクエストを送られても安全な状態を先に作り、画面はその上に載せるため。
